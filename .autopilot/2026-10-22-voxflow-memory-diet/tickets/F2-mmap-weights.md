# F2 — Веса моделей с диска, а не в памяти процесса

**Требования:** G01, R01, R07i
**Зависит от:** F1
**Зона:** `voxflow/src-tauri/src/{ort_session,gigaam,parakeet,models,engine,final_eval}.rs` · `voxflow/src-tauri/Cargo.toml` · `DECISIONS.md` (дополнить D-053)
**Волна:** 4
**Ревью:** да — потеря текста (смена загрузки моделей боевого распознавания)
**Модель:** сильная

## Что должно заработать

Во время диктовки (язык авто: полная GigaAM fp32 + Parakeet int8) footprint процесса заметно ниже нынешних
~1776 МБ после загрузки / ~1850-2111 пик, потому что большие веса энкодеров не копируются в анонимную память
процесса, а читаются из файла (отображение в память, чистые страницы файла не входят в phys_footprint).

## Из брифа, дословно

> «оно потребляет 2 ГБ, это очень много»
> «Полную, но ужать»; после приёмки: «Попробовать дожать, потом релиз»

## Что известно

- Сейчас всё грузится `commit_from_file` (см. `ort_session.rs`, D-053); prepacking выключен только у энкодера Parakeet.
- В ort rc.12 есть `commit_from_memory_directly(&[u8]) -> InMemorySession` и `with_config_entry`; в onnxruntime есть
  `session.use_ort_model_bytes_directly` + `session.use_ort_model_bytes_for_initializers` (для ORT-формата) и
  отображение в память внешних данных (`.onnx` с external data) - что из этого реально даёт чистые file-backed
  страницы для весов, нужно доказать замером, не верить на слово.
- Замер есть: `memory_footprint_bench` в final_eval.rs (`VOXFLOW_TEST_DATA_DIR="$HOME/Library/Application Support/VoxFlow"`, `VOXFLOW_BENCH_N`, `--release`).

## Ограничения

- Тексты на ≥60 записях побуквенно те же; время распознавания не хуже +15% к текущему.
- Модели пользователя в `~/Library/Application Support/VoxFlow` не менять и не удалять; эксперименты - на копиях в scratchpad.
- Диск не удваивать насовсем: если нужен производный файл (`.ort` или external data), то либо он заменяет исходный
  с сохранением проверки целостности (`verify_dir_model`/SHA, D-038/D-040), либо решение с цифрами диска - в D-053
  и в CONCERNS; каталог моделей и `updater.rs` не менять.
- Работать должно на macOS, Linux и Windows (отображение файла есть везде); платформенный код - под cfg, Linux на маке не компилируется.
- Если ни один способ не даёт выигрыша без нарушения ограничений - не тащить в код, вернуть `DONE_WITH_CONCERNS` с цифрами всех попыток (это тоже результат, он уйдёт в D-053).

## Критерии приёмки

- [ ] Замер до и после в одном прогоне `memory_footprint_bench` (после загрузки, пик, после распознавания), цифры в D-053
- [ ] Footprint после загрузки GigaAM fp32 + Parakeet ниже 1776 МБ минимум на 400 МБ, либо попытки с цифрами и причина, почему нет
- [ ] Тексты 60/60 совпадают, время ≤ +15%
- [ ] Повреждённый/подменённый файл модели по-прежнему ловится проверкой целостности (тест)
- [ ] `cargo test --locked --lib`, `cargo clippy --locked --all-targets -- -D warnings`, `cargo fmt --check` зелёные
